
Desde el punto de vista del código Swift las entidades del modelo serán instancias de clases Swift. Así, dada la entidad `Usuario` con ciertos atributos lo que tendremos en Swift es una clase con el mismo nombre y las correspondientes propiedades.

En el `Data Model Inspector` de cada entidad hay una sección titulada `Class` que se ocupa del código generado. Además del nombre de la clase y el módulo (que normalmente dejaremos como están), lo más importante es el campo `Codegen`, la estrategia de generación de código, que tiene tres opciones:

| `Codegen` | Qué genera Xcode | Qué escribimos nosotros | Cuándo usarla |
|---|---|---|---|
| `Class Definition` (por defecto) | Todo: la clase y sus propiedades | Nada | Casi siempre |
| `Category/Extension` | Solo las propiedades y los métodos de las relaciones | La clase | Cuando necesitamos sobreescribir métodos de la clase o añadirle propiedades almacenadas |
| `Manual/None` | Nada | Todo (con ayuda de un asistente) | Raramente |

## El código que genera Xcode

Con `Class Definition` Xcode genera las clases automáticamente al compilar (y normalmente también al guardar el modelo con `Cmd+S`), y las vuelve a generar cada vez que cambiamos el modelo. No las veremos en el navegador de archivos, porque se guardan en un directorio aparte llamado `DerivedData`. No debemos modificarlas, ya que Xcode sobreescribiría los cambios.

> Para ver el código generado podemos hacer `Cmd+clic` sobre el nombre de la clase en nuestro código (o clic derecho y `Jump to Definition`). Xcode abrirá el archivo donde está definida. Esto funciona con cualquier clase, incluso con las del sistema.

Por cada entidad se generan dos archivos. El primero, `Usuario+CoreDataClass.swift`, contiene la clase en sí, que hereda de `NSManagedObject`. Está "vacía", solo tiene alguna anotación necesaria para la maquinaria interna de Core Data:

```swift
@objc(Usuario)
public class Usuario: NSManagedObject {

}
```

El segundo, `Usuario+CoreDataProperties.swift`, es una extensión de la clase anterior con el método `fetchRequest()` y las **propiedades**. Para el `Usuario` del modelo de mensajería serían:

```swift
@NSManaged public var login: String?
@NSManaged public var creditos: Int16
@NSManaged public var fechaAlta: Date?
@NSManaged public var mensajes: NSSet?
@NSManaged public var conversaciones: NSSet?
```

Fíjate en varias cosas:

- Los atributos de tipo objeto (`String`, `Date`...) son opcionales de Swift aunque en el modelo no lo sean, por lo que ya comentamos en la sección anterior. Los numéricos (`Int16`, `Double`, `Bool`...) no lo son.
- **Las relaciones también son propiedades**. `mensajes` representa los mensajes enviados por el usuario, de modo que en lugar de hacer JOINs como en SQL simplemente accederemos a `u.mensajes`. Esto explica el convenio de nombrar las relaciones en singular o plural, ya que en el código queda muy natural: `u.mensajes`, `m.usuario`, `m.conversacion`.
- Las relaciones "a muchos" no ordenadas son de tipo `NSSet`, y las ordenadas de tipo `NSOrderedSet` (por ejemplo, `mensajes` en la clase `Conversacion`).

`NSSet` es el "equivalente" de `Foundation` al tipo `Set` de Swift. Core Data se desarrolló originalmente para Objective-C, y de ahí que use estas clases. Esto tiene dos consecuencias prácticas:

- Los elementos de un `NSSet` no tienen tipo (son `Any`), así que para recorrerlos tendremos que hacer un *cast*, por ejemplo `u.mensajes as? Set<Mensaje>`.
- `NSSet` y `NSOrderedSet` son *inmutables*: no podemos añadir o eliminar elementos de la relación modificando directamente la propiedad.

Para añadir y eliminar elementos de las relaciones "a muchos" Xcode **genera métodos de acceso**. Para la relación `mensajes` del `Usuario`, por ejemplo:

```swift
// MARK: Generated accessors for mensajes
extension Usuario {

    @objc(addMensajesObject:)
    @NSManaged public func addToMensajes(_ value: Mensaje)

    @objc(removeMensajesObject:)
    @NSManaged public func removeFromMensajes(_ value: Mensaje)

    @objc(addMensajes:)
    @NSManaged public func addToMensajes(_ values: NSSet)

    @objc(removeMensajes:)
    @NSManaged public func removeFromMensajes(_ values: NSSet)
}
```

En las relaciones ordenadas se generan además métodos para insertar y eliminar en una posición determinada. Veremos cómo usar todo esto en la sección de CRUD.

## Añadir código propio a las clases

A menudo nos interesará añadir a las clases de las entidades métodos o propiedades calculadas propias. Para eso **no hace falta cambiar el `Codegen`**: basta con escribir una *extensión* de la clase en un archivo de nuestro proyecto (por ejemplo `Usuario+Extras.swift`), que funciona perfectamente con `Class Definition`:

```swift
import Foundation

extension Usuario {
    //número de mensajes enviados por el usuario
    var numMensajes: Int {
        return mensajes?.count ?? 0
    }
}
```

Lo que no podemos hacer en una extensión es añadir propiedades almacenadas, y tampoco es buena práctica sobreescribir en ella métodos de `NSManagedObject`. Por ejemplo, para que la `fechaAlta` de un usuario se rellene automáticamente con la fecha actual al crearlo, sobreescribiríamos `awakeFromInsert()`, que Core Data llama una sola vez cuando se crea el objeto. Para eso necesitamos tener la clase en nuestro código, y aquí es donde entra `Category/Extension`:

1. En el `Data Model Inspector` de la entidad, cambiar `Codegen` a `Category/Extension`. Xcode seguirá generando automáticamente el archivo de las propiedades, pero ya no la clase.
2. Crear un archivo en nuestro proyecto con la clase (el nombre del archivo da igual, pero por convenio se usa `Usuario+CoreDataClass.swift`):

```swift
import Foundation
import CoreData

@objc(Usuario)
public class Usuario: NSManagedObject {
    public override func awakeFromInsert() {
        super.awakeFromInsert()
        self.fechaAlta = Date()
    }
}
```

## Generación manual (`Manual/None`)

En este modo Xcode no genera nada automáticamente, aunque tiene un asistente que crea los dos archivos por nosotros, dentro del proyecto. **Primero hay que poner el `Codegen` de la entidad a `Manual/None`** (si no, la clase estará definida dos veces y el proyecto no compilará: *Invalid redeclaration*) y luego elegir en el menú `Editor > Create NSManagedObject Subclass...`.

El problema es que a partir de ahí Xcode ya no mantiene sincronizado el código con el modelo: si cambiamos las entidades, tendremos que actualizar el código a mano o regenerarlo (perdiendo nuestros cambios). Por eso, en la práctica, es preferible `Category/Extension`.

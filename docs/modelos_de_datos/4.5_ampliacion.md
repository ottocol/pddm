## Otros tipos de datos

Los tipos de atributo que hemos usado (números, cadenas, fechas...) no cubren todos los casos. ¿Y si queremos guardar una imagen, un array o un objeto de otra clase? Si es una clase propia siempre podemos convertirla en otra entidad, pero no siempre tiene sentido complicar el modelo de este modo. Para estos casos tenemos dos tipos especiales: `Binary Data` y `Transformable`.

### Datos binarios

El tipo `Binary Data` se suele usar para imágenes, audio, video, etc. Por ejemplo, para guardar la imagen de perfil de un usuario en un atributo `imagen` de tipo `Binary Data`:

```swift
//la imagen la tendríamos que sacar de algún lado. Sería un UIImage
let imagenPerfil: UIImage = ...
//así obtenemos los datos binarios de una UIImage en PNG 
//con jpegData(compressionQuality:) obtendríamos los datos en JPEG
usuario.imagen = imagenPerfil.pngData()
```

Para recuperar la `UIImage` a partir de los datos guardados usaríamos el inicializador `UIImage(data:)`, y para mostrarla en SwiftUI, `Image(uiImage:)`.

> Guardar datos binarios grandes dentro de la base de datos SQLite la hace crecer mucho y ralentiza las consultas. Si marcamos la opción `Allows External Storage` del atributo en el `Data Model Inspector`, Core Data decidirá automáticamente si guarda los datos en la BD (si son pequeños) o en un archivo aparte (si son grandes), sin que tengamos que cambiar nada en nuestro código.

### Datos transformables

Con los atributos `Transformable` Core Data convierte automáticamente el objeto a binario al guardar y de vuelta a su tipo original al leer. Para que la conversión sea automática el tipo debe ser conforme a `NSSecureCoding`, el mecanismo de serialización heredado de Objective-C (anterior al `Codable` de Swift). Los tipos básicos de Foundation lo cumplen, así como los arrays y diccionarios que los contienen.

Por ejemplo, para guardar los temas de interés de un usuario como un array de `String`, en el `Data Model Inspector` del atributo:

- Definir el tipo del atributo como `Transformable`.
- En `Transformer` elegir o escribir `NSSecureUnarchiveFromData`, el transformador estándar para tipos conformes a `NSSecureCoding`.
- En `Custom Class` escribir el tipo Swift del atributo, en este caso `[String]`. Así la propiedad de la clase generada ya tendrá este tipo.

A partir de ahí trabajamos con la propiedad como un array normal:

```swift
usuario.intereses = ["música", "deporte"]
```

> Si no indicamos ningún `Transformer`, Core Data usa uno antiguo considerado inseguro y muestra un aviso en la consola. Conviene indicarlo siempre.

> Si modificamos el objeto "por dentro" (por ejemplo, `usuario.intereses?.append("cine")`), Core Data puede no detectar el cambio. Lo más seguro es asignar un valor nuevo completo a la propiedad.

Si el tipo no es conforme a `NSSecureCoding` (por ejemplo, un `struct` de Swift) tendremos que escribir nuestra propia clase de conversión heredando de `ValueTransformer`, registrarla al arrancar la app e indicar su nombre en el campo `Transformer`. Podéis ver un ejemplo en [este tutorial](https://www.avanderlee.com/swift/valuetransformer-core-data/). Una alternativa más sencilla para tipos `Codable` es usar un atributo `Binary Data` y hacer nosotros la conversión con `JSONEncoder`/`JSONDecoder` (que vimos en la sesión de persistencia básica) en una propiedad calculada definida en una extensión de la clase.

## Otras características de los atributos

- `Transient`: el atributo no se guarda en el almacenamiento persistente, solo existe en memoria. Es típico de valores que se pueden recalcular fácilmente a partir de otros. En la práctica, muchas veces es más sencillo usar una propiedad calculada en una extensión de la clase.
- `Derived` (desde iOS 13): el valor lo calcula y guarda Core Data a partir de otros atributos o relaciones, por ejemplo el número de mensajes de una conversación (`mensajes.@count`), una versión en minúsculas de un texto o la fecha de la última modificación. Se recalcula al guardar el contexto, no en el momento en que cambian los datos. Es útil sobre todo para optimizar consultas. La documentación de Apple es escasa; podéis consultar [este artículo](https://www.avanderlee.com/core-data/derived-attributes-optimise-fetch-performance/).
- **Índices**: igual que en una base de datos, indexar un atributo acelera las búsquedas sobre él a cambio de ocupar más espacio. En Xcode 15 los índices se definen a nivel de entidad, en la sección `Indexes` del editor.

## Fetched properties

Son similares a las relaciones, pero no son bidireccionales y se basan en una consulta. Por ejemplo, un `Usuario` podría tener una propiedad `mensajesRecientes` con los mensajes que ha enviado en la última semana.

Se crean manteniendo pulsado el botón `Add Attribute` y eligiendo `Add Fetched Property` (también está en el menú `Editor`). Hay que especificar su nombre y el *predicado* (la condición de la consulta); veremos la sintaxis de los predicados en la sesión de consultas.

> Las *fetched properties* no se recalculan automáticamente cada vez que accedemos a ellas: hay que refrescar el objeto explícitamente con `miContexto.refresh(objeto, mergeChanges: true)`. En la práctica es más habitual ejecutar directamente una *fetch request* cuando se necesitan los datos.

## Fetch requests predefinidas

En el editor del modelo también podemos definir *fetch requests* (consultas) con nombre, manteniendo pulsado el botón `Add Entity` y eligiendo `Add Fetch Request`. Las condiciones se definen gráficamente. Desde el código se recuperan con el método `fetchRequestTemplate(forName:)` del modelo (`PersistenceController.shared.container.managedObjectModel`). Veremos las consultas en detalle en la siguiente sesión.

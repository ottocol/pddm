
Como vimos al crear el modelo, para cada atributo podemos especificar en el `Data Model Inspector` una serie de *reglas de validación*: que no sea opcional, un valor mínimo y máximo, una longitud mínima y máxima, una expresión regular... En el modelo de mensajería, por ejemplo, el `login` no es opcional y los `creditos` tienen un valor mínimo de 0.

Core Data no impide que un objeto tenga valores inválidos *en memoria*: lo que asegura es que un objeto no válido no se puede guardar en el almacenamiento persistente. Es decir, **los errores de validación se producen al hacer `save`**, igual que los de restricciones de valores únicos que vimos en la sección anterior, y se tratan de la misma forma.

```swift
let usuario = Usuario(context: miContexto)
usuario.login = "pepe"
usuario.fechaAlta = Date()
usuario.creditos = -1   //el mínimo es 0
do {
    try miContexto.save()
} catch let error as NSError {
    if error.code == NSValidationNumberTooSmallError {
        print("Los créditos no pueden ser negativos")
    }
    print(error.localizedDescription)
    miContexto.rollback()
}
```

El error contiene bastante información: un código que indica el tipo de error y un diccionario (propiedad `userInfo`) con datos como el objeto y el atributo que lo han provocado. En lugar de usar los códigos numéricos podemos usar una serie de constantes que comienzan por `NSValidation`. Las más habituales son:

| Constante | Significado |
|---|---|
| `NSValidationMissingMandatoryPropertyError` | Falta un atributo no opcional |
| `NSValidationNumberTooSmallError`, `NSValidationNumberTooLargeError` | Número fuera de rango |
| `NSValidationStringTooShortError`, `NSValidationStringTooLongError` | Cadena demasiado corta o larga |
| `NSValidationStringPatternMatchingError` | La cadena no encaja con la expresión regular |
| `NSValidationMultipleErrorsError` | Hay varios errores a la vez |

> Cuidado con el último caso: si un objeto tiene **más de un** error de validación (por ejemplo, créditos negativos y además le falta el `login`), el código será `NSValidationMultipleErrorsError` y los errores individuales estarán en un array dentro de `userInfo`, con la clave `NSDetailedErrorsKey`. En ese caso la comparación del ejemplo anterior no se cumpliría.

Si queremos comprobar si un objeto es válido antes de guardar, sin necesidad de llamar a `save`, podemos usar los métodos `validateForInsert()` (para objetos nuevos) o `validateForUpdate()` (para objetos modificados), que lanzan los mismos errores.

## Validaciones propias

Las reglas del inspector cubren los casos más sencillos, pero a veces necesitamos comprobaciones que no se pueden expresar con ellas. Por ejemplo, queremos que el `login` no contenga espacios.

Para ello podemos añadir a la clase de la entidad un método `validate<NombreDelAtributo>`, en nuestro caso `validateLogin`. Core Data lo llamará automáticamente al guardar, y el método debe lanzar un error si el valor no es válido. Como siempre que queremos añadir código a la clase de una entidad, lo hacemos en una extensión en un archivo propio. La signatura del método es un poco "peculiar" por la herencia de Objective-C:

```swift
import Foundation

extension Usuario {
    @objc func validateLogin(_ value: AutoreleasingUnsafeMutablePointer<AnyObject?>) throws {
        //"value.pointee" es el valor que se quiere guardar
        guard let login = value.pointee as? String,
              !login.contains(" ") else {
            throw NSError(domain: "Mensajeria", code: 1,
                          userInfo: [NSLocalizedDescriptionKey: "El login no puede contener espacios"])
        }
    }
}
```

El error que lanzamos aquí es el que recibiremos en el `catch` del `save`, así que podemos usar su `localizedDescription` para mostrarle un mensaje al usuario.

> Si la validación depende de varios atributos a la vez (por ejemplo, que una fecha de fin sea posterior a la de inicio), en lugar de validar atributo por atributo hay que sobreescribir `validateForInsert()` y `validateForUpdate()` en la clase de la entidad, llamando siempre primero a la implementación de `super`. Para eso necesitamos tener la clase en nuestro código (`Codegen` a `Category/Extension`).

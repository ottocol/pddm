
Las operaciones más básicas con Core Data son las de crear, obtener, actualizar y borrar objetos persistentes, es decir operaciones del tipo `Create/Read/Update/Delete` o CRUD. Ya vimos algo de esto en la sesión anterior; aquí lo veremos de modo más sistemático y aplicado a objetos relacionados entre sí.

> En todos los ejemplos suponemos que `miContexto` es el contexto de persistencia (el `viewContext`), que en una vista obtenemos del entorno con `@Environment(\.managedObjectContext)`, como en la sesión anterior.

## Creación

Como ya vimos, los objetos persistentes no se crean con un inicializador cualquiera, sino asociados a un contexto, que será el que gestione su ciclo de vida:

```swift
let u = Usuario(context: miContexto)
u.login = "pepe"
u.fechaAlta = Date()
```

> Si hacemos `Usuario()` sin pasar el contexto, el código compila, pero al ejecutarse Core Data mostrará un error en la consola (*Failed to call designated initializer on NSManagedObject class*) y el objeto no funcionará correctamente.

Los objetos creados existen solo en el contexto ("en memoria") hasta que lo guardemos con `save`.

## Actualización

Una vez tenemos un objeto gestionado (creado con `init(context:)` o recuperado con una *fetch request*) podemos cambiar sus propiedades. Igual que en la creación, los cambios solo se harán persistentes cuando guardemos el contexto:

```swift
u.creditos = 100
//AHORA es cuando se guardan los cambios en el almacenamiento persistente
try miContexto.save()
```

`save` guarda **todos** los cambios pendientes del contexto: objetos nuevos, modificados y borrados. Con la propiedad `miContexto.hasChanges` podemos saber si hay cambios pendientes, y con `miContexto.rollback()` podemos descartar todos los cambios hechos desde el último `save`.

### Errores al guardar

`save` puede fallar, por ejemplo si un objeto no cumple alguna regla de validación o alguna restricción de valores únicos. En el modelo de mensajería el `login` es único y la *merge policy* es la de por defecto, así que si intentamos guardar un usuario con un `login` que ya existe se producirá un error:

```swift
let u2 = Usuario(context: miContexto)
u2.login = "pepe"   //¡ya existe un usuario "pepe"!
u2.fechaAlta = Date()
do {
    try miContexto.save()
} catch let error as NSError {
    if error.code == NSManagedObjectConstraintMergeError {
        print("Ya existe un usuario con ese login")
    }
    //descartamos los cambios que han provocado el error
    miContexto.rollback()
}
```

Hay un detalle muy importante en el código anterior: **cuando `save` falla, los objetos erróneos siguen en el contexto**. Si no hacemos nada, el siguiente `save` volverá a fallar, aunque lo que estemos intentando guardar entonces sea correcto, porque el contexto intentará guardar de nuevo todos los cambios pendientes, incluidos los erróneos. Por eso, tras un error, o bien corregimos el objeto o bien lo descartamos. Con `rollback()` descartamos todos los cambios pendientes; si solo queremos descartar el objeto erróneo, podemos borrarlo del contexto con `miContexto.delete(u2)`.

## Relaciones

### Relaciones "a uno"

Una relación "a uno" se maneja como una propiedad más. Para indicar quién ha enviado un mensaje:

```swift
let m = Mensaje(context: miContexto)
m.texto = "hola a todos"
m.fecha = Date()
m.usuario = u
```

Recordemos que las relaciones tienen inversa, y **Core Data se encarga automáticamente de actualizarla**. Es decir, después de ejecutar el código anterior, el mensaje `m` aparecerá también entre los `mensajes` del usuario `u`, sin necesidad de hacer nada más.

### Relaciones "a muchos"

Para leer una relación "a muchos" tenemos que convertir el `NSSet` en un `Set` de Swift, como vimos en la sección anterior:

```swift
print("Mensajes de \(u.login ?? "")")
if let mensajes = u.mensajes as? Set<Mensaje> {
    for mensaje in mensajes {
        print(mensaje.texto ?? "")
    }
}
```

En una relación ordenada, el `NSOrderedSet` se puede convertir a un array:

```swift
//los mensajes de la conversación "c", en orden
if let mensajes = c.mensajes?.array as? [Mensaje] {
    for mensaje in mensajes {
        print(mensaje.texto ?? "")
    }
}
```

Para modificar una relación "a muchos" usamos los métodos `addToXXX` y `removeFromXXX` que genera Xcode:

```swift
let c = Conversacion(context: miContexto)
c.titulo = "Quedada del viernes"
c.comienzo = Date()
//el usuario u empieza a participar en la conversación
u.addToConversaciones(c)
//añadimos el mensaje m a la conversación
c.addToMensajes(m)
try miContexto.save()
```

De nuevo, Core Data actualiza automáticamente las inversas: `u` aparecerá entre los `participantes` de `c`, y `m.conversacion` será `c`. Por tanto, `c.addToMensajes(m)` y `m.conversacion = c` son equivalentes; podemos usar la que nos resulte más cómoda.

> Si vamos a recorrer a menudo una relación, para no tener que hacer el *cast* cada vez podemos añadir una propiedad calculada en una extensión, como vimos en la sección anterior:
>
> ```swift
> extension Usuario {
>     var listaMensajes: [Mensaje] {
>         let set = mensajes as? Set<Mensaje> ?? []
>         return set.sorted { ($0.fecha ?? .distantPast) < ($1.fecha ?? .distantPast) }
>     }
> }
> ```

## Lectura

Para recuperar objetos del almacenamiento persistente se usan *fetch requests*. En la siguiente sesión veremos cómo poner condiciones y ordenar los resultados; por ahora, para obtener todas las instancias de una entidad:

```swift
let request: NSFetchRequest<Usuario> = Usuario.fetchRequest()
//o bien: let request = NSFetchRequest<Usuario>(entityName: "Usuario")
let usuarios = try miContexto.fetch(request)
for usuario in usuarios {
    print(usuario.login ?? "")
}
```

> Recuerda que hay que indicar el tipo de la variable `request` (`NSFetchRequest<Usuario>`) cuando usamos `Usuario.fetchRequest()`, para evitar ambigüedades con el método del mismo nombre de `NSManagedObject`.

> Ejecutar la *fetch request* con `fetch` es lo que haremos cuando necesitemos los datos en el código. Para mostrar los resultados de una consulta en una vista usaremos `@FetchRequest`, como vimos en la sesión anterior.

Una vez tenemos un objeto, a los objetos relacionados con él accedemos directamente a través de las relaciones, sin necesidad de más *fetch requests*: los mensajes de cada usuario estarán en `usuario.mensajes`.

## Borrado

Para eliminar un objeto llamamos a `delete` sobre el contexto, y como siempre, el borrado no se hace efectivo en el almacenamiento hasta que guardemos:

```swift
miContexto.delete(c)
try miContexto.save()
```

Al borrar un objeto se aplican las *delete rules* de sus relaciones. En el modelo de mensajería:

- Al borrar la conversación `c`, como la regla de `Conversacion.mensajes` es `Cascade`, se borran también todos sus mensajes. Como la de `participantes` es `Nullify`, los usuarios no se borran, simplemente `c` desaparece de sus `conversaciones`.
- Si intentamos borrar un usuario que tiene mensajes, como la regla de `Usuario.mensajes` es `Deny`, al hacer `save` se producirá un error de validación (`NSValidationRelationshipDeniedDeleteError`). Igual que en el caso del `login` repetido, tendremos que tratar el error y deshacer el borrado con `rollback()`.

> Las *delete rules* se aplican al guardar. Si necesitamos que se apliquen antes (por ejemplo para que la interfaz refleje ya los objetos borrados en cascada), podemos llamar a `miContexto.processPendingChanges()`.
